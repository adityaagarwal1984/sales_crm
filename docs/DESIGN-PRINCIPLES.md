# Design Principles for the Prosperr CRM

This is a practical guide for the current React + Spring Boot modular monolith. Apply principles when they make a boundary clearer or a change safer; do not add abstractions just to demonstrate a principle.

## Review snapshot

The backend already separates identity HTTP endpoints, services, repositories, entities, security, and shared error handling. The frontend separates routes, app shell, page components, shared CRM components, and API/auth state. No business workflow entities exist yet, so guidance for SQL, opportunities, meetings, and handover is prospective and must be refined after the tech lead clarifies those workflows.

The most useful near-term improvements are:

- Move admin dashboard aggregation behind a service/query boundary; `AdminUserController` currently injects `UserRepository` directly and issues five role-count queries.
- Keep controllers transport-focused. `AuthController` declares request records inline and `AdminUserService` owns API input/output records; move these into a feature-scoped API DTO package when that contract grows, not as a repository-wide migration now.
- Remove `JpaSpecificationExecutor<UserEntity>` while no specifications are used, or introduce a concrete specification only when approved search/filter needs exist.
- Add pagination before user lists are expected to grow. `AdminUserService.list()` currently loads all users.
- Keep error messages specific by operation. The global `BadCredentialsException` handler says “Invalid email or password,” including when the current password is wrong during password change.
- Keep frontend page files readable and feature-scoped. Current auth/admin pages combine API calls, form state, and rendering; `UserManagementPage` also uses `window.prompt/alert` instead of the shared dialog/form components.
- Add focused frontend tests for login, password change, user management, and server errors. Current frontend tests cover route guards; the backend has one broad integration scenario.

These are improvement candidates, not a mandate to rewrite stable Block 1/2 code during this review.

## Principles and concrete CRM examples

| Principle | Meaning and why it matters | Application and current example | Problem it prevents |
|---|---|---|---|
| **Single Responsibility Principle (SRP)** | A unit should have one main reason to change. Narrow responsibilities make behavior easier to test and review. | `AuthController` maps auth requests; `AuthService` authenticates and changes credentials; `UserRepository` persists identities. Conversely, `AdminUserController.dashboard()` also performs report aggregation through the repository, so future dashboard logic belongs behind a query/service boundary. | Controllers accumulating persistence, rules, and response shaping; pages becoming hard to change without breaking unrelated behavior. |
| **Open/Closed Principle (OCP)** | Extend behavior through a clear seam when variants are real; avoid editing unrelated code for each new case. | `AppRoutes` maps `roleOrder` through `roleNavigation`, so dashboard routes are configuration-driven. Adding a role still changes the Java enum, frontend role order/navigation, and server policies; this is a useful seam, not a claim that role addition is zero-touch. For future qualification rules, use a policy seam only if Prosperr confirms multiple rule variants. | Repeated conditionals scattered across every route, component, and service; premature plugin systems for behavior that has one version. |
| **Liskov Substitution Principle (LSP)** | A subtype must honor the contract expected of its base type. | There is no domain inheritance hierarchy in Blocks 0–2. `UserEntity` references `RoleEntity` through an association instead of `AdminUser`, `BdrUser`, and other subclasses. That actual composition choice avoids inventing subtype behavior before it exists. If a later interface has implementations, tests must verify every implementation honors the same contract. | Subclasses that silently weaken validation, authorization, or state-transition guarantees. |
| **Interface Segregation Principle (ISP)** | Consumers should not depend on operations they do not use. | Services depend on focused Spring interfaces such as `UserRepository`; there are no custom interfaces for every service. `UserRepository` currently adds `JpaSpecificationExecutor`, although no specification is used. Remove that extra capability until a real dynamic-filter use case needs it. | Fat interfaces, unused methods, and layers depending on persistence details they do not need. |
| **Dependency Inversion Principle (DIP)** | High-level policy should depend on stable contracts rather than low-level implementation details. | `AuthService` constructor-injects `UserRepository`, `PasswordEncoder`, and `JwtService`; Spring Data supplies the repository implementation. In React, pages call the shared `api` client rather than building fetch logic in each component. Keep the auth service independent of JDBC details. | Business rules tied to SQL/JPA classes or repeated HTTP configuration. |
| **DRY** | Keep one authoritative implementation for a rule within a given boundary. | Email normalization is centralized in `AuthService.normalize()` and reused by admin operations. Role identifiers necessarily appear in both Java and JavaScript; they are cross-language contracts, so keep them aligned through API documentation/tests rather than pretending one source file can serve both runtimes. `AdminUserController.dashboard()` repeats five role counts and is a concrete duplication to remove when touched. | Fixes applied in only one of several copies; drift between role lists, validation, and metrics. |
| **KISS** | Prefer the smallest design that satisfies the agreed requirement. | One role per account is represented by `UserEntity.role` and a single `role_code` foreign key. This is simpler than a many-to-many role grant model while the product requirement is one assigned role. Keep fixed roles as `RoleCode` until administrators need configurable roles. | Speculative frameworks, generic workflow engines, and role models that add operational cost without a confirmed use case. |
| **Separation of Concerns** | Keep UI, transport, business policy, and persistence in their own boundaries. | Backend flow is controller → service → repository → entity/database. React separates `AppRoutes`, `AppShell`, feature pages, and shared components. The frontend route `Guard` is usability/navigation control; `SecurityConfiguration` enforces the actual role boundary. | UI checks being mistaken for security; database mechanics leaking into HTTP and presentation. |
| **Encapsulation** | Keep state private and expose operations that preserve invariants. | `UserEntity` fields are private; `changePassword()` and `setTemporaryPassword()` update the password hash, `mustChangePassword`, and credential timestamp together. API DTOs omit `passwordHash`. Preserve that invariant and never serialize entities directly. | Partial updates that leave credentials and status flags inconsistent; accidental secret exposure. |
| **High Cohesion** | Keep closely related behavior and data together. | Identity responsibilities live under `identity/` in domain, API, repository, security, and service packages. Future opportunity and SQL rules should be grouped by business capability, not added to a global `CommonService`. | “God” services, utility dumping grounds, and changes with unclear ownership. |
| **Low Coupling** | Minimize knowledge one component needs about another. | `DashboardPage` receives a role and consumes dashboard configuration; the shared shell does not know each row's business meaning. On the backend, `AdminUserController` directly knows repository count methods, which couples transport to persistence and should be reduced when dashboard reporting expands. | One module changing forces unrelated modules to change; controller tests requiring database internals. |
| **Composition over Inheritance** | Assemble behavior from small collaborators/components unless a true subtype relationship exists. | React composes `AppShell` from `Sidebar`, `TopBar`, and routed pages. `UserEntity` composes a role association instead of subclassing by role. Continue composing forms from `FormField`, `Modal`, and button primitives. | Brittle base classes and role-specific branching embedded in shared UI. |

## Block 3 application

- **SRP / Separation of Concerns:** `OrganisationController` and `ContactController` translate HTTP requests; `OrganisationService` owns use-case orchestration and duplicate rules; repositories own persistence queries; React pages own screen state and reuse common form, search, page-header, and pagination components.
- **DIP / Repository:** The service receives Spring Data repositories and the user repository through constructor injection, not through direct SQL or controller access.
- **Encapsulation / DTO:** Organisation/contact JPA entities remain package-domain data. API records explicitly map fields, nested links, and creator labels; no entity is returned directly.
- **KISS / DRY:** Current fixed filters are explicit query parameters and repository predicates. No generalized search-builder or per-field Specification framework was added.
- **Low coupling / modular monolith:** New classes live under `organisation/`; the module depends on the identity repository only to associate the authenticated creator. Future pursuit workflows should reference organisation/contact IDs without merging contact and lead concepts.
- **Trade-off:** Organisation profile mapping includes its contact list, and paged summaries include contact counts. If list volume grows, replace per-row count queries with a grouped projection.

## How to apply this guide

For a new business capability, first state the rule and its owner. Put the rule in a cohesive service/domain operation, validate at the API boundary, persist via a repository, and keep the React page focused on interaction. Add a new abstraction only when there is a real second implementation, policy variation, external integration, or independently testable boundary.
